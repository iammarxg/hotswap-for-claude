# HotSwap backup format

This specification describes `extension/backup-crypto.js`, `backup-schema.js`, and `backup-restore.js`. No remote code, new dependency, or custom cryptographic primitive is used. The version number here is the **file format**, not the extension release version.

## Common container and encoding

UTF-8 JSON plain object with exactly `kind`, `version`, `kdf`, `cipher`, `ciphertext`. `kind` is exactly `hotswap-for-claude-encrypted-backup`. `version` is a JSON integer, either 1 or 2. Object ordering/JSON whitespace are immaterial. Unknown keys, duplicate keys (including escaped aliases), arrays/null in place of objects, and nesting beyond 24 containers are rejected. File.size is checked against the single `MAX_BACKUP_FILE_BYTES = 16777216` constant **before reading the file**; text byte length is also checked. Files are never modified during restore.

All base64 is RFC 4648 standard alphabet, mandatory padding where needed, no whitespace: decoding and re-encoding must reproduce the exact input. Salt is 16 bytes, IV is 12 bytes, ciphertext is between 17 and 10485776 bytes inclusive, including its trailing 16-byte GCM authentication tag. Plaintext is at most 10485760 bytes. Empty JSON payload objects serialize to more than zero bytes, so the 17-byte minimum does not exclude an authentic backup emitted by the original writer.

## Version 1 (permanent reader, original semantics)

`kdf` has exactly `{name:"PBKDF2", hash:"SHA-256", iterations:600000, salt:<base64>}`. Available git history contains only 600000 for this backup format: the allowlist is `{600000}`, checked in addition to integer bounds 100000–5000000. A different historical smart-memory feature used 100000 and is not a v1 account backup.

`cipher` has exactly `{name:"AES-GCM", iv:<base64>, tagLength:128}`. Key length is **256 bits**, implicit in v1. Password bytes are `new TextEncoder().encode(password)`: raw JS string, UTF-8, no trim/normalization; unpaired surrogates become U+FFFD per TextEncoder. PBKDF2-HMAC-SHA-256 derives a non-extractable AES-256 key. GCM AAD is the literal UTF-8 bytes of:

```text
hotswap-for-claude-encrypted-backup:v1
```

There is no trailing newline. Contrary to the initial external premise, the inspected v1 implementation **does have fixed AAD**, but does not authenticate the header via AAD. Header constraints are pinned independently. Never retry v1 with empty AAD or a normalized password. Fixtures are generated by the original `157c59a` encryptor, retained unchanged in `tests/legacy-original.mjs`.

## Version 2 (all new exports)

`kdf` has exactly `{name:"PBKDF2", hash:"SHA-256", iterations:<integer>, salt:<base64>}`. The writer uses 600000; the reader accepts 600000–5000000 inclusive. This is the selected fallback; **Argon2id is not implemented or accepted**. Algorithm changes require an explicit format decision and tests, never fallback after failed decryption.

`cipher` has exactly `{name:"AES-GCM", keyLength:256, iv:<base64>, tagLength:128}`. A fresh 16-byte salt and 12-byte IV come from `crypto.getRandomValues` for every export. No derived key is cached. Password bytes are UTF-8 of `password.normalize("NFKC")`, never trimmed. Derived AES-256 and intermediate PBKDF2 CryptoKeys are non-extractable. Password UTF-8 and plaintext buffers are overwritten in finally; JS strings/objects/browser-internal copies cannot be reliably wiped.

The shared `headerAAD` function constructs the following fields **in this exact order**, from validated constants/integers and decoded salt/IV re-encoded as canonical base64:

```text
kind|version|PBKDF2|SHA-256|iterations|salt_b64|AES-GCM|256|iv_b64|128
```

For example, zero-valued salt and IV with 600000 iterations produce these exact ASCII/UTF-8 bytes (no quotes, BOM, newline, spaces or trailing separator):

```text
hotswap-for-claude-encrypted-backup|2|PBKDF2|SHA-256|600000|AAAAAAAAAAAAAAAAAAAAAA==|AES-GCM|256|AAAAAAAAAAAAAAAA|128
```

The same function is used for encrypt and decrypt. Neither raw JSON text nor JSON property order is AAD. The independent layout/authentication test seals with matching and deliberately mismatched AAD while keeping key/IV unchanged.

## Passwords, errors and dispatch

Export: minimum 12 Unicode code points, maximum 1024 UTF-16 code units before normalization, exact confirmation comparison, advisory common/pattern/length warning. No further strength hard-block. Import: any nonempty string up to 1024 UTF-16 code units; no minimum length. The optional generated-passphrase button is not included, so there is no wordlist dependency.

Version 1 exclusively selects the legacy bytes/AAD/iteration pin; version 2 exclusively selects NFKC/header AAD. Relabeling versions fails, with no retry. Unsupported integer versions produce `Unsupported or newer backup version. Update the extension.` Other invalid file, header, password, tag, truncation, payload, and import-application errors present the same `Couldn't decrypt: wrong password, or the file is damaged or modified.` No raw crypto errors are displayed. Cheap malformed-input rejection deliberately precedes expensive crypto; this is not a constant-time parser or an online password service.

Old `157c59a` readers reject v2 before decryption/storage with their existing `Unsupported or invalid encrypted backup format.` An already installed old extension cannot retroactively gain the newer wording. Existing backup files are never rewritten, downgraded, deleted or replaced automatically.

## Decrypted payload schema and application

`kind` must be `hotswap-for-claude-backup`, and `profiles` is required (0–1000 entries). Optional `exportedAt` and `extensionVersion` are strings of at most 64 UTF-16 code units. All objects below reject unknown keys. No settings/API keys/active-account selection are included or restored.

Profile allowed keys: `id` (string ≤256), `label` (string ≤4096), `email` (null/string ≤1024), `usage` (null/object below), `cookies` (required array ≤1000), `createdAt`, `updatedAt` (finite numbers 0–8640000000000000), `pinned` (boolean). Optional means absent, not wrong-typed. Missing labels retain the historical `Restored account` fallback. As before, imported labels are truncated to 40, new UUIDs assigned, empty-cookie profiles skipped, timestamps defaulted, and only id/label/cookies/timestamps saved.

Cookie required keys: `name`, `value`, `domain`, `path`. Name is ≤256 ASCII HTTP token characters (empty allowed because browser snapshots can contain unnamed cookies). Value is ≤65536 code units, no ASCII control/DEL. Domain is ≤253 lowercase ASCII characters, exactly `claude.ai` or DNS-label subdomains, optionally a leading dot; suffix lookalikes, schemes, ports, and paths are rejected. Path starts `/`, ≤4096, no ASCII control/DEL. Optional booleans: `secure`, `httpOnly`, `session`, `hostOnly`. Optional `expirationDate` is finite within ±8640000000000 seconds, `storeId` ≤256 string, `firstPartyDomain` ≤253 string. `sameSite` is one of `no_restriction`, `lax`, `strict`, `unspecified`. Optional `partitionKey` only allows required `topLevelSite` (1–2048 string), optional `hasCrossSiteAncestor` boolean. Partition/store metadata is retained as snapshot data; the existing cookie writer determines which browser attributes it can apply.

**Cookie-name compatibility tradeoff:** `getAllClaudeCookies` captures every name under Claude domains. There is no finite product name allowlist. The reader validates token syntax/length and restricts domains instead of guessing a closed list from a real user's credentials. This differs from a literal closed-name-list requirement and avoids excluding authentic backups when Claude changes cookie names. If a future product chooses a closed list, coordinate the capture path and version it explicitly.

`usage` permits only `limits`, `subscriptionTier` (≤128 string), `capturedAt` (finite timestamp), with `limits` required. Limit keys are `session`, `weekly`, `sonnetWeekly`, `opusWeekly`, `fableWeekly`; each is null or exactly `{percentage,resetsAt}` (finite percentage 0–1000000, resetsAt null or timestamp). The schema retains the cache metadata in exports; import keeps its existing behavior of not restoring this cache.

Preview decrypts and validates completely, stages a private clone in worker memory for at most two minutes, returns only labels/count, older-format flag and a random token. UI uses `textContent` for labels. Explicit confirmation consumes that token once, prepares new profiles without mutating existing ones, then writes the profiles item once with `chrome.storage.local.set`. No cookies/settings change on import. Cancellation, a superseding preview, expiry, worker restart or any precommit failure cannot apply the staged data. No staged plaintext is persisted. Backup runtime commands are restricted to this extension's popup. Legacy plaintext imports receive the same schema, preview and confirmation; older-format notice recommends manual re-export only.
