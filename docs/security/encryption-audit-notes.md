# Backup encryption audit — before changes

Baseline: `157c59a7a8460ac96351c83bb55b3e83b4a268c6`. Line references in this section refer to that commit, not the subsequently hardened files. No real backup was decrypted, copied, or used as a fixture.

## Complete path

* `extension/popup.html:369–389`: password and confirmation inputs, maxlength 1024. `popup.js:1102 submitEncryptedBackup` reads `.value` verbatim, calls `validateBackupPassword`, compares confirmation exactly, clears both fields before messaging `EXPORT_BACKUP`. No trimming or normalization. Validation failures leave the fields populated (password remains in UI until correction/cancel/navigation). `resetBackupForms` at 1079 clears forms on cancellation, tab navigation and pagehide (1192–1201).
* `popup.js:1153 handleRestoreFileSelected` checks `File.size` against 16 MiB **before** `file.text`, then JSON.parse (1165). No duplicate-key detection. Encrypted envelope stays in popup memory until unlock/cancel. `submitBackupUnlock` at 1182 reads password verbatim and immediately clears input. `restoreBackupData` at 1136 sends envelope/password to `IMPORT_BACKUP` and immediately applies it, with no preview/confirmation.
* `background.js:1721–1729` dispatches export/import. `exportProfilesBackup` at 708 reads all profiles (`getProfiles`, 190), creates `{kind, exportedAt, extensionVersion, profiles}` (715–720), encrypts, downloads encrypted JSON using a data URL, and waits for download completion (722–732). Interrupted download throws rather than reports success.
* `backup-crypto.js:42 deriveKey`: WebCrypto importKey of **TextEncoder UTF-8 of the exact JS password string**, no normalization/trim, then PBKDF2-HMAC-SHA-256, 600000 iterations, AES-GCM **256 bits**, non-extractable, single encrypt/decrypt usage. No derived key cache. WebCrypto TextEncoder replaces unpaired UTF-16 surrogates with U+FFFD.
* `backup-crypto.js:52 encryptBackup`: validates password minimum four Unicode code points / maximum 1024 UTF-16 code units (10–15); serializes payload as UTF-8 JSON (57), maximum 10 MiB; fresh **getRandomValues** 16-byte salt and 12-byte IV on **each call** (59–60). AES-GCM tagLength 128 (63–64). Existing v1 **does use AAD**: literal UTF-8 `hotswap-for-claude-encrypted-backup:v1` (8). It does not bind the header. Ciphertext includes tag, standard base64 (17–40, 66–71). Plaintext byte buffer cleared in finally (73–75); JS strings/objects are GC-managed and cannot be reliably wiped.
* `backup-crypto.js:78 decryptBackup`: pins kind/version, PBKDF2 name/hash/**exact 600000**, AES-GCM name/tagLength before KDF (81–86). Checks nonempty password and maximum 1024 code units (88–89). Base64 decode/re-encode canonical equality (26–40); salt exactly 16, IV exactly 12 bytes (90–91); ciphertext 16 through 10 MiB+16 (92–94). Derived algorithm names/hash/iterations/key size and tagLength are constants, **not** unconstrained file parameters. No unknown-key/plain-object validation. v1 decrypt uses the same fixed AAD (98–100). WebCrypto verifies the tag; no bypass found. Fatal UTF-8 decoding + JSON.parse; only checks kind/profiles array (102–103).
* `background.js:739 importProfilesBackup`: accepts encrypted **and legacy plaintext** backup. Only kind/array checks. Gets existing profiles, skips profiles with no cookies, creates fresh UUIDs, coerces/truncates label, copies cookie array without validation, defaults timestamps, then one `saveProfiles` call (747–768). Does not apply browser cookies or settings during import. Stored snapshots are applied on later account switches via `switchProfile` (579) / `setCookies` (146); refresh/usage also use them (437, 810). New profiles contain id/label/cookies/createdAt/updatedAt/email (509–518); pinned (642) and usage (446 etc.) can also be present in exports. Usage is display/cache metadata, not a backup setting. `getAllClaudeCookies` (106) deliberately collects **all cookie names** for claude.ai and subdomains (85, 102–110); there is no historical cookie-name allowlist to infer.
* `getProfiles` / `saveProfiles` at `background.js:190–196` store raw profile objects, including session cookies, in **unencrypted chrome.storage.local**. Separate `secret-vault.js:49 seal` encrypts Gemini API keys in IndexedDB; that is not profile encryption and not included in backups.

## Errors / secret lifecycle

`decryptBackup` catches decryption, fatal decoding, parsing failures with one constant message (105–106), clears plaintext bytes in finally (108). Header/base64/size failures have different messages (before that catch). Popup displays error.message (1147, 1167), background's outer handler forwards raw err.message (1802–1803). No password/key/payload logging or persistence was found in the encryption calls or import/export handlers. Passwords survive only in form fields, local variables, and transient runtime messages; no reliable JS string erasure is possible.

`setCookies` at `background.js:178` logs the full `details` object (including cookie **value**) on browser rejection; line 182 logs raw browser exceptions. This is reachable after importing and then switching to a backup profile. Existing stored sessions are intentionally persisted; the no-persistence requirement cannot literally apply to the final, user-confirmed restored profiles without removing the product's functionality.

## History evidence

Executed `git log --all --oneline -- extension/backup-crypto.js` and `git log --all -p -G 'PBKDF2|iterations' -- '*.js'`. Available local history has one backup crypto introduction, **157c59a**, and only **600000** shipped v1 backup iterations. Historical `27fe4ed` smart-memory.js uses 100000 for a different format/feature, not this backup kind. Preserve v1's 600000 pin (allowlist `{600000}`, within requested 100000–5000000 bounds). This establishes available local history, not unseen remote branches or historical archive binaries.

## Confirmed findings

* **High:** imported cookie scopes/fields are unvalidated (`importProfilesBackup:760`), allowing a malicious validly encrypted/plaintext backup to store arbitrary cookies for later application. Host permissions constrain browser writes but are not a payload schema. Add domain/type/bounds validation, preview and confirmation.
* **Medium:** rejected cookie restore logs can expose active session credential values (`setCookies:178`). Remove credential-bearing objects and raw errors from those log statements; regression-test rejected-cookie paths.
* **Low:** password fields remain populated after export validation failure (`submitEncryptedBackup:1109–1111`). Clear them on every submit attempt, including invalid/mismatched passwords; regression-test.
* **Hardening gaps:** no duplicate/unknown-key rejection, no complete payload schema or import preview, 4-character export minimum, no header-bound AAD. Existing size and KDF caps already prevent iteration-bomb derivations. No salt/IV reuse, weak randomness, sub-256-bit AES, extractable derived keys, or tag-verification bypass confirmed.

## Decisions to validate during implementation

Keep v1 raw UTF-8, fixed AAD, AES-256 and iteration pin unchanged. Add v2 with separate normalized password encoding and header-bound AAD. A closed cookie-name list conflicts with the deliberate all-Claude-cookie snapshot contract: constrain cookie-name syntax/length and Claude domain boundaries; report this compatibility tradeoff rather than inventing a list from one user's sensitive backup. Argon2id requires measured Chrome/Firefox MV3 compatibility and lifetime/memory/device evidence before adoption; if those cannot be established, select the specified WebCrypto PBKDF2 fallback, and record missing measurements explicitly.
